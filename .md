Burger Bombs — Project README
What We're Building
A restaurant management system prototype for Burger Bombs, a Philippine-based burger business. The system is designed as an offline-first, hybrid cloud POS that demonstrates how a restaurant can operate reliably even with unstable internet.

The Core Problem We're Solving
Most restaurant POS systems fail when the internet goes down:

Orders are lost

Customers get frustrated

Kitchen staff work blind

Sales stop recording

Our solution: The POS saves every order to the browser's local database (IndexedDB) first, then syncs to the cloud when connectivity is available. No order is ever lost.

What the Prototype Demonstrates
Feature	What It Shows
Offline-First POS	Orders save locally first, sync later
Sync Engine	Background worker pushes orders to backend when online
Idempotency	Duplicate retries don't create duplicate orders
Hybrid Cloud	Local operations + cloud sync for online store
Real-Time Kitchen Display	Orders appear instantly via WebSockets
Delivery Tracking	GPS tracking with Leaflet/OpenStreetMap

Key Technical Concepts
Offline-First Pattern
All writes go to IndexedDB via Dexie.js first

UI never waits for network

Orders are never lost, even offline

Outbox Pattern
Every action (e.g., "create order") is written to an outbox table inside the same transaction

A background worker reads pending outbox items and sends them to the backend

On success, the outbox entry is marked sent

On failure, it retries up to 5 times

Idempotency
Every action has a unique mutationId (UUID)

Backend uses a processed_mutations table with ON CONFLICT DO NOTHING

If the same mutationId arrives twice, the second is ignored

Result: No duplicate orders, even with network retries

How to Run the System
Prerequisites
Docker Desktop installed

Node.js (v20+ recommended)

PowerShell (Windows) or Bash

Start the Database
powershell
cd burger-bombs
docker-compose up -d
Apply Schema (first time only)
powershell
docker cp db/schema.sql burger-bombs-postgres-1:/tmp/schema.sql
docker exec -i burger-bombs-postgres-1 psql -U burger_user -d burger_bombs_local -f /tmp/schema.sql
Seed Menu (first time only)
powershell
docker exec -i burger-bombs-postgres-1 psql -U burger_user -d burger_bombs_local -c "INSERT INTO menu_items (name, price, available) VALUES ('Classic Burger', 120.00, TRUE), ('Cheese Burger', 140.00, TRUE), ('Double Patty', 180.00, TRUE), ('Bacon Burger', 160.00, FALSE), ('Fries', 60.00, TRUE), ('Coke', 40.00, TRUE);"
Start Backend
powershell
cd backend
npm run dev
# → [backend] http://localhost:4000
Test the Backend
powershell
# Health check
curl http://localhost:4000/health
# → {"ok":true}

# Get menu
curl http://localhost:4000/api/menu
# → [{"id":1,"name":"Classic Burger","price":120,"available":true}, ...]

# Test idempotency — send same mutationId twice
curl -X POST http://localhost:4000/api/sync -H "Content-Type: application/json" -d "{\"mutationId\":\"11111111-1111-1111-1111-111111111111\",\"type\":\"CREATE_ORDER\",\"payload\":{\"total\":240,\"items\":[{\"id\":1,\"name\":\"Classic Burger\",\"price\":120,\"qty\":2}],\"createdAt\":\"2025-01-01T00:00:00Z\"}}"
# → {"ok":true}

# Send again
curl -X POST http://localhost:4000/api/sync -H "Content-Type: application/json" -d "{\"mutationId\":\"11111111-1111-1111-1111-111111111111\",\"type\":\"CREATE_ORDER\",\"payload\":{\"total\":240,\"items\":[{\"id\":1,\"name\":\"Classic Burger\",\"price\":120,\"qty\":2}],\"createdAt\":\"2025-01-01T00:00:00Z\"}}"
# → {"ok":true,"duplicate":true}   ← idempotency works

The Demo That Sells the System
Open POS at http://localhost:5173

Add items to cart, click "Place Order"

Watch "Pending sync: 1" appear in header

After ~5 seconds, "Pending sync: 0" (synced to backend)

Kill the internet (DevTools → Network → Offline)

Place 3 more orders — all succeed locally, "Pending sync: 3"

Restore internet — all 3 orders sync within 5 seconds

Verify in database: SELECT COUNT(*) FROM orders; → 4 total, no duplicates

The pitch to restaurants: "Your POS never loses an order, even when the internet dies. It syncs when it can. No more angry customers, no more lost sales."

Why This Architecture Is Feasible for a Broke Developer
Concern	Reality
Hosting cost	$0 for local demo (Docker + localhost)
Cloud cost	Neon free tier (0.5 GB) for prototype
Vercel cost	Free for non-commercial demo
Payment gateway	Start with cash + manual GCash; add PayMongo later
Total cash needed	$0–$7/month (only if you need Render Starter to avoid cold starts)
The key insight: Run everything locally for demos. The cloud is only needed when you want to show the "online store + local POS sync" story. For restaurant demos, local is actually better — zero latency, no internet dependency.
